## 1. Verdict

**The crate selection is broadly sound and the version discipline is real.** Across six domains, roughly sixty crates and versions were checked against the crates.io API on 2026-08-24. Exactly one does not exist. Every other version cited is not merely real but is the current latest stable — that is an unusually good result for a document of this size, and the crates chosen are, with a handful of exceptions listed below, the ones a careful person would pick. The rejections of `fundsp`, `biquad`, `rdev`, `slint` and `dioxus` all survive scrutiny; several survive for better reasons than the plan gives.

Three things would actually change the outcome of the project.

**First: the plan's primary echo canceller cannot be built for two of its three targets.** `webrtc-audio-processing` 2.1.0 does not compile on `x86_64-pc-windows-msvc` or `i686-pc-windows-msvc`. This is not a version nit — §2.3(a) recommends it as the conservative choice and labels `sonora` the risky one, and on Windows that is exactly backwards. Windows is the overwhelming majority of this app's users, and without an APM the port ships an audible regression on day one. This must move to a blocking item at gate G2, and the gate must be a green `cargo build --target i686-pc-windows-msvc` from whichever crate wins — including `sonora`, whose i686 status is *also* unproven.

> **Adopted 2026-08-24, more strongly than recommended.** This section asked for the injection path to be split into a 32-bit helper. It was removed outright instead, so the `i686` target is gone rather than isolated: no NASM requirement, no MSVC alignment hazard, and `libwebrtc` is available to `P3`. The paragraph stands as written because its argument is why.

**Second: the `i686-pc-windows-msvc` target is the largest available lever on the project's risk profile, and the plan never examines it.** §7.1 says "i686 is required for the injection path", and §3.3 confirms injection is already feature-gated and 32-bit-only. That single target is what forecloses `libwebrtc` (LiveKit's binding to the real Chromium stack, which would supply AEC3, NS, AGC, Opus with FEC/DTX, RTP/RTCP and NetEQ as one dependency — its build script maps only `x86_64 → x64` and `aarch64 → arm64`, with no 32-bit x86 path: https://github.com/livekit/rust-sdks/blob/main/webrtc-sys/build/src/lib.rs). It is what puts a NASM requirement on the build machine once TLS enters the tree (aws-lc-rs ships prebuilt NASM objects for Windows x86-64 only: https://aws.github.io/aws-lc-rs/requirements/windows.html). It is where MSVC's 4-byte alignment quirk creates a real unsoundness hazard for exactly the struct-parsing code `acl-game` is full of (rustc platform support, footnote `win32-msvc-alignment`, and https://github.com/rust-lang/rust/issues/112480). **Split the injection path into a small 32-bit helper process talking to a 64-bit main client, and rows 13 and 14 of §2.2 drop from High risk to Low, the neteq gate becomes optional rather than existential, and the integrated-pipeline option becomes live.** That deserves an explicit paragraph and an explicit decision, not silence.

**Third: the dependency policy in §7.6 is unsatisfiable against the plan's own dependency list, and a policy that fails on day one gets switched off in week one.** Rule 3 blocks duplicate major versions. Measured on the *best possible* networking configuration (webrtc + ureq + tokio-tungstenite + tokio, no reqwest, no rust_socketio) there are still 13 duplicate-major pairs, because the RustCrypto ecosystem is mid-migration and `rtc-dtls` itself declares `rand ^0.10.1` and `rand_core ^0.6.4` side by side. On the GUI side, `arboard` (unavoidable, it arrives through `egui-winit`'s default `clipboard` feature) requires `windows-sys >=0.52.0, <0.61.0` against eframe's `^0.61.2`, and `arboard` requires `x11rb ^0.13` against the plan's `x11rb` 0.14.0. Rule 3 has to become a warning plus a dated, reviewed allow-list (`bans.skip` / `skip-tree`), or the team learns to ignore the gate — and the gate is the plan's central supply-chain claim. The same applies to `cargo-vet`: across Mozilla's, Google's and the Bytecode Alliance's shared audit sets, there are **zero** audits for `cpal`, `opus`, `webrtc-audio-processing`, `neteq`, `sonora`, `rubato`, `ringbuf`, `symphonia`, `webrtc`, `str0m`, `tokio-tungstenite`, `reqwest`, `rust_socketio`, `windows`, `windows-sys`, `x11rb`, `sysinfo`, `directories`, `global-hotkey`, `eframe`, `egui`, `winit`, `rfd`, `arboard`, `self_update` or `self-replace`. Making cargo-vet blocking from phase 1 (04-implementation-plan.md §4.3, item 3) will produce a wall of exemptions and no assurance. Say that plainly in §6.1 rather than letting the supply-chain table imply coverage that does not exist.

## 2. Findings that change the plan

### 2.1 `serde_json 1.0.229` does not exist — the plan does not build

**Plan:** §7.2, Support table: `| serde / serde_json | 1.0.229 |`, under a header reading "All versions verified against crates.io on 2026-08-23."

**Actually:** `https://crates.io/api/v1/crates/serde_json/1.0.229` returns HTTP 404. The latest `serde_json` is **1.0.151**, published 2026-07-20 (https://crates.io/api/v1/crates/serde_json). `serde` 1.0.229 is real (2026-07-18); the two crates have not shared a version number since 2019, and collapsing them into one table cell produced a version that cannot resolve.

**Do:** split the row; pin `serde 1.0.229` and `serde_json 1.0.151`. Then re-verify every version in the audio, network, platform and GUI tables independently — this review re-checked them and they held, but the header's verification claim is now known to be untrue, so it should not be trusted for anything not checked here.

**Buys:** the build. Nothing else in this document matters if the first `cargo build` fails. *(Confidence: verified.)*

### 2.2 The primary APM does not build on Windows

**Plan:** §2.3(a) recommends `webrtc-audio-processing` `=2.1.0` with the `bundled` feature as the conservative choice for AEC3/NS/AGC/HPF; §7.2 pins it exactly.

**Actually:** the crate and version are real (2026-05-13), but PR #102 — opened 2026-08-08, still open, unmerged — enumerates three sequential MSVC failures, each visible only after the previous is fixed: `build.rs` passes `-Wno-unused-parameter` unconditionally and `cl` reads it as `/Wno-unused-parameter` (`Command line error D8021`); WebRTC's designated initializers hit `error C7555: use of designated initializers requires at least '/std:c++20'`; and the symbol-prefixing step's `objcopy --redefine-sym` misses COFF references, producing ~156 `LNK2019` unresolved externals. Issue #34, titled "Windows build", has been open since 2023-09-27. The CI matrix in `.github/workflows/rust.yml` is `[ubuntu-latest, macos-latest]` — there is no Windows job, so nothing would catch a regression even after #102 lands. docs.rs has never successfully built any 2.x (issue #90). PR #102 is scoped to `x86_64-pc-windows-msvc` only; `i686` has no evidence of ever being attempted.
(https://github.com/tonarino/webrtc-audio-processing/pull/102, /issues/34, /issues/90, https://docs.rs/crate/webrtc-audio-processing/2.1.0/builds)

Two secondary points: the crate uses `license-file = "COPYING"` so crates.io reports the licence as non-standard and cargo-deny will reject it as unknown until a `[licenses.clarify]` entry exists; and the `bundled` build requires meson, ninja and clang/gcc on every CI runner and every contributor's machine, on top of MSVC — a materially larger build-time execution surface than §6.2 describes.

**Do:** make `sonora` 0.2.0 the default APM and demote `webrtc-audio-processing` to a Linux-only comparison baseline used in testing. Keep the trait boundary §2.3(a) already proposes. Add to gate G2, as **preconditions of the recommendation rather than follow-up actions**: (a) `sonora` builds and passes its test suite on `i686-pc-windows-msvc` — this is genuinely unproven, its README validates only on Ubuntu x86_64 and its SIMD paths are SSE2/AVX2/NEON; (b) an A/B echo-return-loss-enhancement measurement of the two on Linux, where both build, using real speaker-and-mic captures.

**Buys:** an echo canceller that exists on the platform that has the users. §2.3(a)'s framing — "known-good audio, heavier build" vs "lighter, but young and unproven" — should be rewritten. `sonora` is BSD-3-Clause, pure Rust (no C++ toolchain, no meson, no git submodule — it removes the single largest `build.rs` surface §6.2 identifies), ported from WebRTC M145, and its README states it is validated against the C++ reference test suite of 2,400+ tests, benchmarked within 1.07–1.24x of the C++. Running the reference implementation's own conformance suite is a stronger correctness argument than 104k downloads. Its real risks are different from the ones the plan names: bus factor 1 (dignifiedquire, 209 of 221 commits), two releases, an AI-assisted port acknowledged in its own history section, and the unproven i686 build. Those are gate items. *(Confidence: verified; sonora's i686 status explicitly unverified.)*
(https://github.com/dignifiedquire/sonora, https://crates.io/api/v1/crates/sonora)

### 2.3 `neteq` as written pulls a web framework, a CLI parser, a second `cpal` and a second Opus — and fails the plan's own cargo-deny rule

**Plan:** §7.2 pins `neteq = "=0.9.1"`, with the note "young (38 k downloads); measured at gate G2".

**Actually:** `neteq` 0.9.1's manifest sets `default = ["native", "audio_files"]`, and `native = ["cpal", "clap", "ropus", "rand", "axum", "tokio", "tower", "tower-http", "env_logger"]`. Written as the plan writes it, the audio crate pulls axum 0.7, clap 4.5, **cpal 0.15 — three majors behind the pinned 0.18.2** — tower 0.4, tower-http 0.5, and `ropus ^0.12`: a pure-Rust Opus port, sole author, first published 2026-04-18, 2,913 total downloads. videocall-rs switched to it deliberately (PR #872, merged 2026-06-30); that is their call and not one this project should inherit by default.

`default-features = false` does not fully fix it. `ringbuf ^0.3` and `thiserror ^1.0` are **non-optional** in `neteq` 0.9.1, so the build gets `ringbuf` 0.3.3 (2023-03-31) beside the plan's 0.5.1 and `thiserror` 1 beside 2.0.20 — two majors of a lock-free concurrency primitive in one binary. §7.6(3) blocks exactly that.

Also relevant and absent from the plan: upstream issue #716, open since 2026-03-05, "need to investigate perf (audio concealment especially) on windows with wifi power mgmt on". An open concealment bug on this app's primary platform is the single most relevant fact about this crate. And the download figure is misleading: 37,714 total against 29,386 in the last 90 days — 78% of all-time traffic in one quarter for a monorepo workspace member with its own CI. That is a build-traffic pattern, not field exposure.
(https://crates.io/api/v1/crates/neteq/0.9.1/dependencies, https://github.com/security-union/videocall-rs/issues/716, https://github.com/security-union/videocall-rs/pull/872)

**Do:** keep `neteq`, but write the gate conditions down. (1) `default-features = false`, mandatory. (2) Implement `neteq::codec::AudioDecoder` — a public, dyn-compatible trait with three methods — against the `opus` crate, so libopus stays the only codec in the binary and `ropus` never ships. (3) Resolve the `ringbuf`/`thiserror` duplicates explicitly in `deny.toml` (this is the *only* one of the three options that does not also require re-deciding neteq — the duplicate exists solely because of it, and disappears if G2 drops the crate). (4) Fix §3.3's playback diagram: NetEQ is pull-based — accelerate, preemptive expand and expand all drive decode on demand — so `NetEq → OpusDecoder` as a linear pipe is not how it works, and the `AudioDecoder` trait is what makes it work. (5) Add "ship a well-tuned fixed jitter buffer with Opus in-band FEC and PLC" to §2.3(b)'s fallback list — that is what most P2P voice apps do, and the plan's only stated fallback is porting the reference NetEQ, which is a multi-week job. (6) Test concealment specifically on Windows with Wi-Fi power management on. (7) Measure against a plain fixed-delay buffer under the same network emulation, or the gate has no baseline to judge against.

**Buys:** security — a second Opus implementation and a web framework in the address space of a proximity chat client are attack surface for nothing. Performance — one codec, one ring buffer, one `cpal`. *(Confidence: verified.)*

### 2.4 `rust_socketio` cannot be used even briefly — it fails four §7.6(3) rules on contact

**Plan:** §7.5, "The one stale dependency": start with `rust_socketio` 0.6.0 in phase 4, replace it as a scheduled task inside the phase.

**Actually:** it pulls `backoff` 0.4.0 → RUSTSEC-2025-0012 (unmaintained, `patched` empty — no fixed version exists) and, through backoff, `instant` 0.1 → RUSTSEC-2024-0384 (unmaintained, `patched` empty). It also pulls `reqwest ^0.12` against the plan's 0.13.4 and `tokio-tungstenite`/`tungstenite` `^0.21` against the plan's 0.30.0. §7.6(3) blocks unmaintained advisories *and* duplicate majors. **CI is red from the first commit of phase 4**, with no fix available. It additionally adds `native-tls` + `schannel`, a third TLS stack.
(https://crates.io/api/v1/crates/rust_socketio/0.6.0/dependencies, https://rustsec.org/packages/backoff.html, https://rustsec.org/packages/instant.html)

**Do:** write the client from the start, on `tokio-tungstenite` 0.30.0 — which changes status from "fallback" to primary transport. The job is smaller than the plan's 400-line estimate, because the app is **already WebSocket-only**: `src/renderer/Voice.tsx:873` and `src/renderer/LobbyBrowser/LobbyBrowser.tsx:108` both pass `transports: ['websocket']`. Connecting directly with `transport=websocket` deletes HTTP long-polling, the `ping "probe"`/`pong "probe"`/upgrade handshake, and base64 binary framing from the specification surface entirely (binary is base64-wrapped only on the polling transport). What remains: five Engine.IO v4 packet types (open/close/ping/pong/message), five Socket.IO v5 types (CONNECT/DISCONNECT/EVENT/ACK/CONNECT_ERROR), the grammar `<type>[<attachments>-][<namespace>,][<ackid>]<json>` with the namespace omitted for `/`, and one ack-id counter for `join_lobby`.
(https://socket.io/docs/v4/engine-io-protocol/, https://socket.io/docs/v4/socket-io-protocol/)

Name these as explicit tests: **(a) heartbeat direction — in Engine.IO v4 the SERVER sends `ping` and the client replies `pong`, reversed from v3;** get it backwards and everything appears to work until the server's `pingTimeout` fires. (b) Honour `pingInterval`, `pingTimeout` and `maxPayload` from the open packet rather than hard-coding them. (c) The CONNECT ack carries a Socket.IO `sid` distinct from the Engine.IO `sid`. (d) Ack-id leak if the server never acks `join_lobby`. (e) A `CONNECT_ERROR` must be distinguishable from a transport close, so an auth rejection does not drive the reconnect policy. Reconnection itself is not the transport's problem: `src/renderer/reconnectPolicy.ts` is 34 lines of pure functions with no transport coupling and its tests port across unchanged — the transport's only obligation is to report "closed" honestly.

Alternatives checked and rejected: `socketioxide` is server-only and ships no client, so the implied symmetry with the server port does not exist; `tf-rust-socketio` 0.8.1 is a maintained fork but single-org with 9,875 downloads; `sioc`/`eioc` 0.5.0 are a clean protocol split with ~400 downloads and three months of existence.

**Buys:** security — removes two crates under permanent unmaintained advisories, a second reqwest, a second tungstenite and a third TLS stack. Performance — 127 transitive crates down to zero new ones. This is the textbook write-our-own case: the dependency is unusable under the project's own gate, the protocol is publicly specified and small, and the dangerous parts (TLS, WebSocket framing) stay in `tokio-tungstenite`. *(Confidence: verified; the line estimate is a judgement.)*

### 2.5 `self_update` 0.44.0 ships two live CVSS 7.5 advisories, and the plan never names the mechanism that satisfies its own signing requirement

**Plan:** §7.2 lists `self_update 0.44.0`. §6.1 requires "a detached signature against a key embedded in the binary"; §6.4 lists it as a checkbox.

**Actually:** `self_update` 0.44.0 declares `quick-xml ^0.38` as **non-optional** — it compiles into every build, including a GitHub-only one. quick-xml 0.38.x is affected by RUSTSEC-2026-0194 (quadratic duplicate-attribute check, CVSS 7.5) and RUSTSEC-2026-0195 (unbounded namespace-declaration allocation in `NsReader`, CVSS 7.5). Both are fixed only in `>= 0.41.0`, which `^0.38` cannot reach. There is no lockfile or feature escape. The plan's own cargo-deny advisory gate fails against its own pinned version.

The fix exists only in the unreleased 1.0 line: `1.0.0-rc.6` moves quick-xml to `^0.41` **and makes it optional**, bumps `zipsign-api` 0.1→0.2 and `zip` 6→8. §7.6(1) bars pre-releases from a shipped build, so today there is no version of this crate that satisfies both §7.6(1) and §7.6(3).

Also: §7 never names the signature mechanism. It exists — `self_update`'s `signatures` feature uses zipsign (ed25519) and `UpdateBuilder::verifying_keys([...])` embeds a public key in the binary. Without it, the port is a *lateral move* from `electron-updater`: same trust root (GitHub serves both artefact and digest, so a compromised release is undetectable), minus electron-builder's blockmap differential download, plus a live advisory.
(https://crates.io/api/v1/crates/self_update/0.44.0/dependencies, https://rustsec.org/advisories/RUSTSEC-2026-0194.html, https://rustsec.org/advisories/RUSTSEC-2026-0195.html, https://docs.rs/self_update/0.44.0/self_update/backends/github/struct.UpdateBuilder.html)

**Do:** track the 1.0 line and pin exactly once stable, configured `default-features = false, features = ["ureq", "rustls", "github", "signatures", "checksums", "archive-zip", "compression-tar-gz"]`, with `.no_confirm(true)` and `.show_output(false)` — the defaults block on an interactive stdin prompt a windowed GUI cannot answer. If 1.0 has not stabilised when phase 7 arrives, write the updater: a GET of the GitHub Releases API, a semver compare, download artefact plus detached signature, verify with an embedded ed25519 key via `minisign` 0.9.1 or `zipsign-api` 0.2.1, then `self-replace` 1.5.0. That is not writing crypto — the verification stays in a purpose-built crate. Keep the private key **offline**, not in a release-workflow secret.

Reject `axoupdater`: its `lib.rs` downloads `{app}-installer.ps1` from the release and executes it via `powershell -ExecutionPolicy ByPass`, with no signature and no checksum on the script — TLS to GitHub is the entire integrity control, and for a client §6.3 says may run elevated that is worse than today. Reject `velopack`: its integrity model is Authenticode ("signing needs to be performed by Velopack itself"), so without a certificate you are back to TLS plus checksum, and it requires the .NET `vpk` tool in the release pipeline of a project whose premise is escaping a heavy runtime.
(https://raw.githubusercontent.com/axodotdev/axoupdater/main/axoupdater/src/lib.rs, https://docs.velopack.io/packaging/signing)

**Do also:** for an elevated client, verify then **hand the user the verified installer path** rather than executing it. The code-signing certificate and the update-integrity problem are different problems — a certificate costs money and buys SmartScreen reputation; an ed25519 keypair costs nothing and buys integrity. Solve the second now.

**Buys:** the first update integrity this project has ever had that survives a GitHub account compromise. *(Confidence: verified; the "~150 lines" estimate is unverified.)*

### 2.6 The plan's stated reason for choosing `webrtc-rs` over `str0m` is stale; the real reason is TURN, and it is stronger

**Plan:** §2.3(d) describes `webrtc` 0.20.3 as "a port of Pion" exposing "essentially the same `RTCPeerConnection` surface", says the 237-line `peer.ts` "maps onto it almost one-to-one", and rejects `str0m` because its P2P path "has had less testing".

**Actually, three corrections:**

1. **Not a Pion port.** Since 0.20.0 (2026-07-31 — three weeks before the plan was written), `webrtc` is a thin async wrapper over a new sans-IO `rtc` core, self-described as "a clean, ergonomic, runtime-agnostic rewrite on top of a Sans-I/O core". The audit's "eight-month-old core" was **refuted** — the accurate statement is that the code the plan would ship reached 0.20.0 three weeks before the plan, with four patch releases since. Single crates.io owner (rainliu) against str0m's two; the wider contributor graph could not be checked (GitHub API rate-limited).

2. **"str0m is sans-IO and would test nicer" is no longer a differentiator** — but only partly. The `rtc` core is sans-IO; the `webrtc` crate the plan depends on is the async wrapper with `runtime-tokio` on by default, so str0m's deterministic "feed time in, drain `poll_output`" testing model still requires dropping to `rtc` directly. str0m's testing edge shrinks; it does not vanish.

3. **The decisive argument is absent.** str0m's README states plainly that TURN is out of scope — "We consider TURN similar to enumerating local network interfaces – it's a way of obtaining sockets" — and its feature table marks TURN ❌. This app depends on TURN: `src/renderer/validateClientPeerConfig.ts` validates a server-pushed `forceRelayOnly` flag plus `turn:`/`turns:` URLs with username and credential. Choosing str0m means writing or sourcing an RFC 8656 client (Allocate, Refresh, CreatePermission, ChannelBind, long-term credentials with realm/nonce/stale-nonce) — a multi-week job in exactly the wrong category for hand-writing. `webrtc-rs` ships `rtc-turn`.
(https://raw.githubusercontent.com/algesten/str0m/main/README.md, https://crates.io/api/v1/crates/rtc/0.20.3/dependencies)

**Do:** rewrite §2.3(d) around TURN. Pin exactly (`=0.20.3`) on the same footing as `neteq` and the APM — the maintainer states a minor bump may carry breaking changes, and 0.21.0-beta.2 already adds `crypto-ring`/`crypto-aws-lc-rs` features and tightens a `build()` bound. Correct the API-mapping estimate: `peer.ts` lines 188–192 null all five event handlers before `pc.close()`, and that teardown is precisely how the 1.0.0 fixes avoid acting on events from a connection being replaced. `webrtc` 0.20 takes a single `Arc<dyn PeerConnectionEventHandler>` at `PeerConnectionBuilder::with_handler()` with **no per-event detach**, so that pattern must become a generation counter or an atomic detached flag inside the handler. That is where offer glare and stuck-in-`new` come back, and "almost one-to-one" hides it.

Record str0m's genuine advantages as known gaps rather than pretending the chosen option dominates: str0m's default `dimpl` backend advertises DTLS 1.2/1.3 while webrtc-rs's DTLS version support is unconfirmed; str0m ships a GCC-style bandwidth estimator and pacer while `rtc` ships TWCC feedback but no estimator on top of it. Also record: `rtc-dtls` pulls `rkyv ^0.8.17`, used only in `state.rs` marshal/unmarshal for DTLS session resumption — an API this app will never call, so not reachable, but rkyv's 2026 advisories (including RUSTSEC-2026-0233, use-after-free on crafted archives) will appear in every `cargo audit` run and need a documented `deny.toml` note plus a confirmation the port never calls those two functions.

**Buys:** security — TURN is on the critical path because the app forces relay, and a WebRTC stack without a TURN client is not a candidate. Reviewability — a stated reason that survives a reader checking it. *(Confidence: verified; "str0m's tree is a third the size" was **unverifiable** and should be dropped or measured with `cloc`.)*

### 2.7 The signalling server has an unauthenticated 64 MiB inbound message hole that cannot be closed from configuration

**Plan:** §3.4 lists `main.rs # axum + socketioxide, TLS, graceful shutdown`; §7.3 lists `tower 0.5.3` as "middleware"; §6.3 declares the server threat model out of scope.

**Actually:** engineioxide applies its `max_payload` (100 KB default) only on the polling transport — `src/transport/polling.rs:182`. The WebSocket path at `src/transport/ws.rs:120` constructs `WebSocketConfig::default().read_buffer_size(...)` and nothing else, so tungstenite's defaults stand: **64 MiB max message, 16 MiB max frame**. `transport/mod.rs` merely advertises `max_payload` in the handshake OPEN packet, which a hostile client ignores. `EngineIoConfig` exposes no WebSocket size knob at all.

**Critically, and correcting the original audit: this cannot be fixed at a reverse proxy.** nginx's `client_max_body_size` stops applying at the Upgrade; nginx has no post-upgrade frame directive and neither does Caddy's `reverse_proxy`. Both relay frames. The only routes are an upstream PR to engineioxide exposing `WebSocketConfig::max_message_size`, or a fork. **This should be recorded as an accepted risk with an upstream issue filed, not as a config line.**

**And a second structural point that governs everything else on this server:** HTTP-layer rate limiting stops mattering the moment a client upgrades. engineioxide's `ws.rs` calls `hyper::upgrade::on(req)` and takes over the connection; after that, every Socket.IO event for the rest of the session passes through **zero tower layers**. Any `GovernorLayer`, `TimeoutLayer` or `RequestBodyLimitLayer` protects the handshake only. Per-event limiting has to live inside the socketioxide handlers, as a per-socket token bucket in socket `Extensions`.

**Do:**
- `socketioxide = { version = "0.18.6", features = ["tracing", "extensions", "state"] }`. **Zero features are default.** Without `tracing`, socketioxide's internal error paths — including the rejected-malformed-payload log — emit absolutely nothing.
- Add `tower-http` 0.7.0 to §7.3. The plan's "tower replaces middleware" is misleading: tower ships protocol-agnostic middleware (limit, timeout, retry, buffer, load-shed) but **no HTTP-aware middleware at all** — no CORS, no body cap, no HTTP tracing, no panic catching. Those are in tower-http: `limit::RequestBodyLimitLayer`, `timeout::RequestBodyTimeoutLayer` (slow-body / R-U-Dead-Yet, which hyper's 30 s header timeout does *not* cover), `cors::CorsLayer`, `trace::TraceLayer`, `catch_panic::CatchPanicLayer`.
- **CORS on the HTTP routes only.** §3.5 says the OBS overlay "is unaffected" by the port. It is affected: `Settings.tsx:1157` builds `https://obs.aucl.greluc.me/?...&server=${settings.serverURL}`, a browser page on a different origin. socketioxide ships no CORS handling. *(Superseded in part on 2026-08-24: this review was written while Engine.IO polling was still on the table, and the polling handshake is an XHR that would have needed a `CorsLayer` on the socket.io route. The server is now websocket-only, and a WebSocket upgrade is not a CORS request — so the socket.io route needs no `CorsLayer` and must not get an `Origin` allow-list either. The overlay page is instead switched to `transports: ['websocket']`. `CorsLayer` still belongs on `/health` and `/lobbies`, which a browser does fetch with XHR. See `03-target-architecture.md` §3.4 and `04-implementation-plan.md` §4.2 item 6.)*
- Fix shutdown ordering: `with_graceful_shutdown` waits for in-flight connections, and a WebSocket never completes on its own. Call `SocketIo::close().await` *first* or every deploy needs SIGKILL.
- Tighten `connect_timeout` from 45 s to ~10 s: a client can currently open a connection, never join a namespace, and hold a slot for 45 seconds.
- Bound registry growth. The serde-based validation genuinely fixes the *malformed* class — verified in source: `handler/message.rs` returns before invoking the handler on any extractor error, and every handler is `tokio::spawn`ed so a panic is confined to one task. It does nothing for the *volumetric* class: unbounded lobby count, members per lobby, total sockets, relayed `signal` blob size, and no eviction of empty lobbies. That is the likeliest next outage and it needs numeric caps in the plan.
- **Do not use `std::sync::Mutex` with `.unwrap()` for the lobby registry.** One panic while holding the lock poisons it permanently, converting a one-request panic into a total persistent outage — strictly worse than the Node original, which would at least have restarted. Use `parking_lot::Mutex` or `DashMap`.
- Terminate TLS at a reverse proxy (nginx: `limit_req` and `limit_conn` are built in; Caddy's rate limiter is a **non-standard community module requiring an xcaddy build**, so do not describe it as a config line) and bind axum to localhost. That removes aws-lc-rs from the server binary entirely. It does *not* solve the WebSocket frame cap — one bullet fewer in the pitch, but cert rotation, ACME, per-IP connection caps and slow-body timeouts all still land.
- Harden the process: unprivileged user, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `MemoryMax=`, `LimitNOFILE=`. One systemd unit file, highest security-per-effort item in the document.

**Buys:** security. The one class of bug this server has actually suffered was an unauthenticated remote DoS, and §6.3 declares that threat model out of scope for the component the plan proposes to ship *first*. *(Confidence: verified in engineioxide 0.17.6 and socketioxide 0.18.6 source.)*

### 2.9 `reqwest` is the wrong shape for three GETs and adds a second crypto stack plus a NASM requirement on i686

**Plan:** §7.2 lists `reqwest 0.13.4` for "Offset store, hat collection, update check".

**Actually, measured locally with cargo 1.97.1 rather than estimated:** reqwest 0.13.4 with default features resolves 94 crates; `ureq` 3.4.0 resolves 27. Whole-domain: the plan's §7.2 network row (webrtc + rust_socketio + tokio full + reqwest + tokio-tungstenite) resolves **272 crates for x86_64-pc-windows-msvc with aws-lc-rs 1.18.0, aws-lc-sys 0.44.0, ring 0.17.14, native-tls 0.2.18, rustls 0.23.43 and schannel all present** — three separate crypto stacks. Substituting ureq gives **228 crates with only ring and rustls**.

reqwest 0.13 silently changed its crypto foundation: `default-tls = ["rustls"]` and `rustls = ["__rustls-aws-lc-rs", "dep:rustls-platform-verifier", "__rustls"]`. Meanwhile `rtc` 0.20.3's default feature is `ring`. So the plan's build links two C/asm crypto libraries where one would do. And because aws-lc-rs ships prebuilt NASM objects for Windows x86-64 only, the default build imposes NASM on `i686-pc-windows-msvc` — a target §7.1 declares mandatory. ureq defaults to ring, the backend webrtc-rs already links.

**Do:** replace with `ureq` 3.4.0 (2026-08-08, MIT OR Apache-2.0, 184M downloads, no RustSec advisory ever). Two conditions: drive it from `tokio::task::spawn_blocking` (ureq 3.x is synchronous — arguably a feature, since three update GETs then cannot stall the runtime the voice path shares); and enable the `platform-verifier` feature while disabling `rustls-webpki-roots`, or you ship bundled Mozilla roots that miss enterprise CAs and only update on a crate bump. `self_update` 0.44.0 already declares an optional `ureq ^3.0.6` backend alongside its `reqwest ^0.13` one, so both §7.2 entries move together. Do **not** drop to hyper directly — redirects, proxies, connection pooling and TLS plumbing are the write-our-own trap. Note that `ureq` and `str0m` share an author (algesten); if str0m is ever revisited, that is a concentration worth recording.

**Buys:** performance and build simplicity — 44 fewer crates and two fewer crypto stacks. Security — one audited crypto backend instead of three, and no NASM dependency on the mandatory 32-bit target. *(Confidence: verified by local re-measurement.)*

### 2.10 `cpal` is right, but the subsystem this app has a bug class in is the newest part of it

**Plan:** §7.2 lists `cpal 0.18.2` as "the standard choice", risk Low–Medium.

**Actually:** 0.18.0 (2026-06-06) was a ground-up rework — unified `Error`/`ErrorKind`, redesigned `StreamInstant`, streams no longer auto-start, a new `realtime` feature, and a **brand-new PipeWire host that now takes priority over PulseAudio and ALSA on Linux**. The plan's Linux backend is ten weeks old, and the plan does not say so. Four open issues sit directly on the device-change path this app already has a bug class around: #1302 (open, 2026-08-08) — a process-wide `OnceLock` `IMMDeviceEnumerator` created in one thread's STA and used after that thread exits, producing `STATUS_ACCESS_VIOLATION` **from safe code**; #1339 (2026-08-23) — PR #1267 stopped emitting `DeviceChanged` on the belief WASAPI does not auto-reroute, and the reporter demonstrates it does, costing ~50 ms extra to re-create the stream; #1332 (device connect/disconnect notifications); #1255 (Bluetooth switching mid-stream). The good news the plan also omits: 0.18.0 *added* `ErrorKind::DeviceChanged`, automatic WASAPI rerouting for default streams, and `DeviceNotAvailable` on ALSA disconnection — cpal is moving toward solving this app's problem, and the app will be an early user of the fix. #1302 is partially in flight (the unreleased CHANGELOG already carries "WASAPI: Device enumeration no longer panics if the COM enumerator fails to initialize"), so budget for tracking rather than necessarily carrying a patch. Note #1302 is triggered by short-lived threads touching cpal first — which a device-hotplug watcher thread would do.

Verified good news on the real-time path: I read `src/host/wasapi/stream.rs` rather than trusting the claim. The scratch buffer is hoisted before the loop; the only `clone()`s inside are COM `AddRef` refcount bumps. cpal itself neither allocates nor locks on the callback path, so §3.2's rule 1 is achievable.
(https://github.com/RustAudio/cpal/issues/1302, /1339, /1332, /1255, https://raw.githubusercontent.com/RustAudio/cpal/master/CHANGELOG.md)

**Do:** keep cpal with three conditions. (1) Make device-change and hot-plug a **named gate item**: a manual test that unplugs a USB mic, switches the Windows default device, and connects/disconnects a Bluetooth headset while a call is live, on Windows and on PipeWire, before G2 sign-off. (2) Track #1302 and #1339 explicitly. (3) Name `cubeb` 0.38.0 in §7.2 as the documented fallback with a written trigger condition, and keep the device layer behind a trait from day one exactly as the plan already does for the APM. Mozilla's shared cargo-vet set carries 9 audits for `cubeb`, 10 for `cubeb-sys`, 11 for `cubeb-core` — against **zero** for cpal — though the chain stops at 0.34.1, so adopting cubeb would still leave 0.34.1 → 0.38.0 to audit locally. Do **not** go direct to WASAPI + ALSA/PipeWire: enumeration, format negotiation and hot-plug are exactly where the bugs live.

**Buys:** the app's most-reported symptom class is "my microphone stopped working". This is the one place where the port can measurably improve on it, and it needs a test, not a crate. *(Confidence: verified.)*

### 2.11 Smaller findings, still worth acting on

**`opus` 0.4.0 was published the same day the plan verified versions, and its entire content is a supply-chain change.** Published 2026-08-23 20:51 UTC; the commits are "Replace audiopus_sys with maintained opusic-sys (#27)", "Update opusic-sys to 0.7.3", two `cargo update`s, and a version bump. The major bump exists solely because the `-sys` backend moved. Adopting a one-day-old release whose only change is swapping the C build layer is the opposite of the conservatism §7.6(1) claims. **Pin `=0.3.1` for the gate work and move to 0.4.0 only after `opusic-sys` 0.7.5 is demonstrated linking on `i686-pc-windows-msvc`** — its CI covers macos/windows/ubuntu but not i686, so 32-bit libopus via cmake+MSVC is likely but unverified. That is a one-hour experiment. Keeping libopus is right; `ropus`, despite claiming bit-exactness, has 2,913 downloads and four months of existence, and a codec is the canonical case where a decade of hardening beats a clean-room rewrite.

**`rubato` needs a pin and a purpose.** Four breaking majors in four months (2.0.0 April, 3.0.0 May, 4.0.0 July, 5.0.0 August 2026), each locked to a matching major of `audioadapter`. Pin `=5.0.0` on the same footing as the APM. v5.0.0's headline fix was "index out-of-bounds panic in async resamplers during ramped ratio transitions" — a panic that shipped through the whole 4.x line, and §6.2 correctly identifies a panic on the audio thread as a denial of service. Two questions the empty Note column does not ask: (a) Opus, the APM and the mixer all run at 48 kHz, so scope the resampler to devices that are not 48 kHz rather than putting an unconditional stage in §3.3's capture chain; (b) **the plan has no answer for capture/render clock drift.** Two independent device clocks diverge over a long session and the jitter buffer slowly fills or starves — indistinguishable in a bug report from the neteq problems G2 exists to catch. rubato 4.0.0 added a `Slip` resampler for exactly this ("a clutch for matching two almost-equal sample rates by occasionally slipping a frame, hidden by a short crossfade"). The plan mentions neither the problem nor the tool. There is no maintained competitor — `speexdsp-resampler`'s highest non-yanked version is 0.1.0 from 2020, `samplerate` last released 2021.

**Drop `symphonia`.** §7.2 gives its role as "Decodes the reverb impulse response". `static/sounds/reverb.ogx` is 55,589 bytes, ships inside the application, and never changes. The plan pulls a general-purpose media demuxer and decoder framework into the shipped runtime to read a compile-time constant. Decode it once in the `xtask` the plan already has and embed raw PCM with `include_bytes!`. **Corrected figures:** one second of 48 kHz stereo is 192 KB as i16 and 384 KB as f32 — the original audit doubled both. The actual duration of `reverb.ogx` is not established anywhere, so have the xtask print the decoded frame count and record the real size. This removes a parser from the runtime, makes the convolver testable with no I/O, makes the impulse response byte-identical across platforms, and removes an MPL-2.0 licence question (the header is plain MPL 2.0 with no "Incompatible With Secondary Licenses" clause, so it *is* GPL-compatible — but the plan asserts GPL compatibility only for egui and never records this check).

**Drop `arboard`.** It is already in the tree: `eframe` → `egui-winit` with the `clipboard` default feature, which pulls `arboard ^3.6` with `image-data` plus `smithay-clipboard` on Wayland — better Wayland coverage than a bare arboard. Grepping `src/` for `clipboard`, `writeText` and `navigator.clipboard` returns nothing, so the copy button is new functionality, not parity. **Correcting the original audit:** a direct declaration would *unify* with egui-winit's and adds no duplicate crates, and does not pull `image` "a second time" — cargo unifies it. The honest reason is that the line is redundant and creates version-drift surface. (The windows-sys 0.60/0.61 duplicate is arboard's `>=0.52.0, <0.61.0` bound, and it exists whether or not the direct line does.)

**Drop `askama`** — but as a proportionality call, not a security finding. It is a healthy crate with 45M downloads. It is a proc-macro template engine, its build-graph cost, and a `templates/` build input, for **one** status page, in a project whose §7.6(5) demands a "why not standard library" answer. **Correcting the original audit on two points:** askama supports inline `source = "..."` so "no build-input directory" is not a differentiator, and hand-rolled escaping is not *safer* than askama's — both escape the same five characters and neither is context-sensitive inside an unquoted attribute. Escaping is your problem either way. The strongest part of the argument is that `/health` and `/lobbies` go through serde_json and need no templating at all.

**Write the localisation layer.** `fluent` 0.17.0 was published 2025-05-23, `projectfluent/fluent-rs` was last pushed 2026-03-27, bus factor 1 — the least-maintained crate in the GUI stack. And nothing it offers is used: across all 37 `static/locales/*/translation.json` there is not one `{{interpolation}}` placeholder and not one `_plural` key, and `src/renderer/language/i18n.ts` configures only `resources`, `fallbackLng` and `escapeValue: false`. Plurals, gender, selectors, date/number formatting, the FTL expression language — all unused, for 128 constant strings. Keep the JSON byte-for-byte, load it with the `serde_json` already present, flatten nested keys once at startup into a map, and write `fn t(&self, key: &str) -> &str`. Under 100 lines, zero dependencies. This also avoids unbudgeted risk the plan does not mention: `static/locales/README.md` points translators at Crowdin (`https://crwd.in/bettercrewlink`), so converting to `.ftl` means reconfiguring that project and asking every community translator to learn FTL escaping. §2.2 rates row 10 Low risk / 1 week counting only the xtask. (`rust-i18n` also reads JSON but expects its own `locales/<locale>.json` layout, so it does not read the existing files in place.)

**Drop `sysinfo`.** The app uses it to find one process by name. That costs 26 s of clean build across 25 crates, drags in `ntapi` → `winapi` 0.3.9 (last released 2020-06-26 — six years, and no RustSec advisory, so §7.6(3) misses it by construction) plus 107 MB of MinGW import libraries for targets this project never builds, and buys **3 ms per call** over a 25-line Toolhelp32 scan (re-measured: 12.50 ms vs 9.04 ms). Feature trimming does not help — it removes only macOS-gated crates. Windows: `CreateToolhelp32Snapshot` + `Process32FirstW`/`NextW`, one unsafe block, one feature group. Linux: `read_dir("/proc")` + `/proc/<pid>/comm`, no crate at all, a direct transliteration of `native/memoryjs/lib/linux/process.cc:15-59`. Separately: neither figure should be paid on a poll loop — `src/main/GameReader.ts:95` re-runs `getProcesses()` on every check. Find the PID once, keep the handle, re-scan only on read failure. Deleting sysinfo is also what unblocks moving the project's own Win32 to `windows-sys`.

**Add `nix` for the Linux memory reader.** §3.3 specifies `LinuxProcess` as `process_vm_readv` + `/proc/<pid>/maps`, and §7 lists no crate providing it — so the implied base is raw libc with a hand-written unsafe wrapper. `nix::sys::uio::process_vm_readv` is a **safe fn** whose lengths derive from the slices passed in, so the Linux implementation of the trait can contain zero unsafe blocks. `rustix` has no equivalent and cannot substitute. nix is also the best-audited crate in the platform domain (11 Google + 6 Mozilla cargo-vet audits). Two things the plan must add regardless of crate: **`ptrace_scope` is never mentioned** — `process_vm_readv` performs a `PTRACE_MODE_ATTACH_REALCREDS` check, so Yama `ptrace_scope=1` (the Ubuntu and Debian default) blocks reading a non-descendant same-uid process, and the game is not our child. §6.3 says only that reading memory "requires the same privilege level as the game", which is the Windows story. And **do not port the short-read behaviour**: `native/memoryjs/lib/linux/memory.cc:13-16` responds to a failed read with `memset(buffer, 0, size)`, silently substituting zeros. Make it an error — which means §3.3's `fn read(&self, addr: u64, buf: &mut [u8]) -> Result<()>` should be `read_exact`, so the returned count can be compared against `buf.len()`.

**`windows-sys` over `windows`, but only after sysinfo goes.** Measured on this machine with the same release profile: `windows` 0.62.2 with the ten needed feature groups builds in ~8.0–8.6 s across 15 dependencies; `windows-sys` 0.61.2 with equivalent groups builds in ~2.30 s across 2. **Correcting the original audit: the ratio is ~3.5x, not 7x** — the claimed 1.13 s did not reproduce. Final binaries differ by exactly 4,096 bytes, so drop binary size from the argument entirely, and both need **exactly 5 unsafe blocks** at the call site, because every Win32 free function in `windows` is an `unsafe fn` too. What `windows` genuinely buys is `Result`-returning calls, newtype flags, `Default` on structs and `Owned<HANDLE>` RAII — all reproducible in ~150 lines over windows-sys, which the project wants anyway since §6.2 already mandates one checked helper. But `sysinfo` forces `windows` into the tree via `windows >=0.62, <0.63`, and shipping two binding crates is worse than either alone. **Unreported hazard:** windows-rs master is at 0.100.0 with a wholesale restructure — feature names go from `Win32_Foundation`-style paths to lowercase header names, edition 2024, MSRV 1.95. The next release rewrites every `use` and every feature name. Budget for it.

**On `zerocopy` vs `bytemuck`: keep zerocopy, but for the right reason.** The original audit's justification — that `TryFromBytes` handles bools and enums where bytemuck cannot — is **refuted**: bytemuck has `CheckedBitPattern` with a derive macro for exactly that. The argument that survives is `KnownLayout`'s support for trailing-slice DSTs, i.e. a .NET array header plus `[T]`, which bytemuck has no equivalent for. Note the audit trail does not favour zerocopy either: bytemuck has 16 Google audits, zerocopy 8 Google + 1 Mozilla, and **both audit chains stop short of the pinned 0.8.56** (Mozilla's delta ends at 0.8.27, Google's `ub-risk-1` certification is at 0.8.14). Given §6.2's own reasoning — zerocopy parses attacker-influenced memory — the 0.8.27 → 0.8.56 delta is one of exactly two things worth a real human cargo-vet audit, the other being the update crate.

**Do not introduce a `WH_KEYBOARD_LL` hook.** §3.3's platform table lists `SetWindowsHookEx(WH_KEYBOARD_LL)` as the Windows key hook, and §6.1 counts "a low-level keyboard hook" among the 4,390 C/C++ lines the port converts. Grepping `native/` and `src/` returns zero occurrences of `SetWindowsHookEx`, `WH_KEYBOARD_LL` or `LowLevelKeyboardProc`. `native/node-keyboard-watcher/src/lib/keyhandler.cpp:55` is a 60 ms `GetAsyncKeyState` poll, aliased to `XQueryKeymap` on Linux. **The plan proposes to introduce a low-level hook while describing it as a port.** A `WH_KEYBOARD_LL` callback runs on the installing thread's message pump; until it returns, every keystroke on the desktop is blocked, and exceeding `LowLevelHooksTimeout` (300 ms default) gets it silently unhooked. That is a desktop-wide latency dependency for zero gain over a poll that already works and intercepts nothing. Keep the poll. Free Linux improvement while you are there: `getkeystate.cpp` calls `XOpenDisplay`/`XCloseDisplay` on **every** key check — with x11rb, open one connection at startup.

> **Update, 2026-08-24.** Two facts this finding rests on have expired, and the finding is left standing rather than rewritten because its conclusion has not. `native/node-keyboard-watcher` is gone: it carried no licence at all, which disqualified the project from the free code-signing programmes for open source, and `native/uiohook-napi` replaced it. So grepping `native/` now returns `SetWindowsHookEx(WH_KEYBOARD_LL)` and `WH_MOUSE_LL`, and `getkeystate.cpp` no longer exists. The latency objection is softer against libuiohook than against a naive hook — it runs on its own thread with its own pump and dispatches to JavaScript non-blocking on a copied event — but it is not gone, and the port has no licensing reason to take a hook at all. **Keep the poll.** See §6.1.

The plan's rejection of `global-hotkey` reaches the right conclusion for the wrong reason. It says push-to-talk needs key-up; `HotKeyState::{Pressed, Released}` has existed since **0.4.0**. The genuine disqualifiers, any one sufficient: `RegisterHotKey` swallows the key, so a PTT key the game also uses never reaches the game *(this is the load-bearing point and it is not stated on MSDN — cite a demonstration)*; registration fails with `ERROR_HOTKEY_ALREADY_REGISTERED` if Discord or OBS owns the combination; its Windows implementation spawns a fresh OS thread per `WM_HOTKEY` and polls `GetAsyncKeyState` with a 50 ms sleep, so up to 50 ms of extra open microphone after release (a privacy tail, not just latency); and Linux is X11-only. The `rdev` rejection is correct and the date verifies exactly.

**Two GUI corrections to record before anyone acts on them.** The plan's reason for rejecting `iced` does not hold up: `iced::window::enable_mouse_passthrough` exists in 0.14.0, `iced::window::Window: HasWindowHandle + HasDisplayHandle`, and `window::run` gives raw handle access. The defensible reasons are 8.6x the download base (22.0M vs 2.58M), five egui minor releases in the 14.6 months between iced 0.13.1 and 0.14.0, immediate mode matching a UI that is a pure function of a 5 Hz snapshot, and egui's `ViewportBuilder` exposing `with_mouse_passthrough`/`with_transparent`/`with_always_on_top` as declarative builders rather than runtime Tasks. Record the counterpoint honestly: iced ships `tiny-skia` as a **default** feature, so it has a software renderer fallback out of the box and eframe does not. And `slint`'s rejection should be sharpened: of its three licence options (`GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0`) only GPL-3.0-**only** is usable here, and combining it into a GPL-3.0-or-later work leaves the distributable effectively GPL-3.0-only — the project silently loses its "or later" option. `dioxus`'s rejection should read "its *default* desktop backend is a webview, and the non-webview alternative (Dioxus Native, Blitz + Vello) is experimental as of 0.7", or a reader who has seen the 0.7 notes will think the plan is out of date.

**The overlay is the weakest-evidenced part of the GUI plan.** §3.2 puts it in a second winit window inside the client process. egui #4451 — "Window transparency not working in eframe on Windows OS" — has been open since 2024-05-03 with 25 comments and activity on 2026-08-23; transparent windows render solid black for many users and the workarounds are **renderer-specific** (one confirmed fix on Windows 11 + Intel UHD is literally `renderer: eframe::Renderer::Glow, multisampling: 1`; another commenter on 2026-04-18 reports that even under glow, deferred viewports still render black — #3632). eframe picks one renderer per process for all viewports, so a single-process design forecloses the only known fix. #4091 — "Immediate viewport would crash with ViewportBuilder settings fullscreen + transparent + always_on_top" — is precisely the overlay's configuration, and is open. **Prototype a transparent click-through window on Windows x64, Windows i686 and Linux in phase 1, before the 8–12 week GUI phase begins.** It is the single highest-information cheap experiment in the whole plan. A separate overlay process is very probably right: it lets the main window use wgpu while the overlay uses whatever actually produces a transparent surface on that machine, and it makes a driver fault in cosmetic code a restart of a child process rather than a dropped voice session. *(Note: the CPU-rasterise alternative via `softbuffer` is not currently available — alpha support is unreleased on master and no published softbuffer, latest 0.4.8, has it; the route would be tiny-skia presented through `UpdateLayeredWindow` / ARGB+XFixes, which is a larger job than §2.2's Medium / 2–3 wk row 8 covers.)*

## 3. Where to write our own code instead

Five places. Each with an honest cost.

**1. The Socket.IO / Engine.IO v4 client — 250–400 lines.** *Cost:* five failure modes that all present as "it works until it doesn't" — reversed heartbeat direction (silent until `pingTimeout`), hard-coded `pingInterval`/`pingTimeout`/`maxPayload` instead of reading the open packet, conflating the Socket.IO `sid` with the Engine.IO `sid`, leaking ack ids when the server never acks, and treating `CONNECT_ERROR` as a transport close so an auth rejection drives the reconnect policy. All five are testable against the real Node server and the ported socketioxide server. *Why it wins:* the dependency is unusable under the project's own gate, the spec is public and small once polling is gone, and TLS and framing stay in `tokio-tungstenite`.

**2. The lock-free SPSC queues — roughly 120 lines each, unverified estimate.** *Cost:* higher than the number suggests. A bounded SPSC ring over a fixed array with two `AtomicUsize` indices and acquire/release ordering is textbook, and it can be verified under Miri and Loom in CI — which is more assurance than an unaudited third-party crate (`ringbuf` has zero cargo-vet audits in any shared set, and it is an unsafe-heavy primitive on the boundary between the real-time thread and everything else). But the app also wants the direct-slice access `ringbuf`'s own tagline advertises — writing into the callback's buffer without a copy — and that is the part that grows past the textbook version. *Why it might win:* it eliminates the ringbuf 0.3/0.5 duplicate outright. *Why it might not:* that duplicate exists solely because of `neteq`, so if G2 drops neteq the whole reason evaporates. Decide this **after** G2, not before.

**3. Process enumeration — ~25 lines Windows, ~15 lines Linux.** *Cost:* essentially none. The Windows half is one `unsafe` block around a frozen Win32 API; the Linux half is `std::fs` and is a direct transliteration of code already in `native/`. The only failure mode is forgetting a case-insensitive UTF-16 compare. *Buys:* 25 crates and 26 s of build time gone, plus `winapi` 0.3.9 and 107 MB of MinGW import libraries out of the tree, plus the freedom to move to `windows-sys`.

**4. The localisation lookup — under 100 lines.** *Cost:* essentially none, because the corpus genuinely has no interpolation and no plurals. The one thing to get right is the English fallback chain. *Buys:* removes the least-maintained crate in the GUI stack, and — more valuable — removes an unbudgeted Crowdin migration and a retraining burden on 37 locales' worth of volunteer translators.

**5. A log-directory size cap — ~40 lines.** *Cost:* one design trap. Run it on a timer or at the rotation boundary, never per write, or a `metadata()` syscall lands in the logging path. *Why it is needed:* `tracing-appender` 0.2.5 rotates on **time only** (NEVER/MINUTELY/HOURLY/DAILY/WEEKLY) and `max_log_files` bounds the file **count**, not the bytes. DAILY + max_log_files(3) bounds you to three files of unbounded size — one audio device failing to open in a loop and today's file grows until the disk does. And the failure modes on a full disk, read from the source rather than inferred: `worker.rs` swallows write errors with `Err(_) => {}` and a `// TODO: Expose a metric for IO Errors` comment; flush errors `eprintln!`, which a windowed Windows binary has nowhere to send; `rolling.rs` keeps a stale writer if the next file cannot be created; `RollingFileAppender::new()` **panics** (`.expect("initializing rolling file appender failed")`) so a read-only log directory takes the process down at startup — use `Builder::build()`, which returns a `Result`; and `non_blocking` is lossy by default (`DEFAULT_BUFFERED_LINES_LIMIT = 128_000`, `is_lossy: true`), which is the right default for a real-time app but means `error_counter()` needs wiring to something. Do not take a 0.1.x crate to avoid forty lines.

**Two places explicitly not to write our own,** because the boundary matters: the codec and the echo canceller. libopus is fifteen years of adversarial hardening, continuous fuzzing, and the same library Chromium ships. AEC3 is an adaptive filter whose failure mode is silent. Also **not** the TURN client (multi-week RFC 8656 surface — and this is what decides the WebRTC library choice), **not** hyper-direct HTTP, and **not** the XDG portal file-chooser conversation on Linux, where two of rfd's recent commits are literally "handle broken portal implementations gracefully" and "distinguish empty multi-item responses from cancellations". *(On rfd: the original audit's claim that dropping it removes a `windows-sys` duplicate is **refuted** — rfd 0.17.2 requires `^0.61`, unified with eframe's `^0.61.2` — and its "~60 lines of IFileOpenDialog" is understated: rfd's own Windows backend is ~24 KB across four files covering COM apartment init, wide-string filter specs, `IShellItemArray` multi-select and the cancellation HRESULT.)*

## 4. Where the plan is right, and should not be second-guessed

- **The version discipline.** Sixty-odd versions checked; one wrong. Everything else is the current latest stable, and no crate is fabricated. That is rare.
- **Keeping libopus.** §2.3(b) is right that Opus is not a risk. `ropus` claims bit-exactness against the fixed-point reference, which would be impressive, and it has 2,913 downloads and four months of existence. A codec is where a decade of hardening beats a clean-room rewrite.
- **Rejecting `fundsp`.** The plan says matching a crate's coefficient conventions is more work than five formulas. True, and the sharper version is that fundsp is a graph-and-combinator library with its own audio-rate execution model — adopting it for five nodes means adopting that model and then fighting it for Web Audio parity. The abstraction is the cost, not the coefficients.
- **Rejecting `biquad`, and for a stronger reason than the plan gives.** §3.3 uses "lowpass 2300 Hz Q −15". Web Audio §1.13.5 defines two alpha terms — `α_Q = sinω₀/(2Q)` and `α_{Q_dB} = sinω₀/(2·10^(Q/20))` — and the coefficient blocks for `lowpass` and `highpass` use the **decibel** form, while bandpass/notch/allpass/peaking use the linear one. So Q = −15 dB ≈ 0.178, a heavily damped filter, perfectly legal. A generic crate takes a linear quality factor and will either reject −15 or silently produce something else entirely. Document this — a future reviewer will otherwise re-litigate it. **Two corrections to the implementation notes:** the spec does **not** mandate Direct Form I ("There are multiple ways of implementing the type of filters available through the BiquadFilterNode... The formulas in this section describe the filters that a conforming implementation MUST implement" — the MUST attaches to the coefficients, not the topology). Choose Direct Form I because it keeps input and output history separate; do not claim the spec requires it. And do not reflexively reset filter state on coefficient change: the spec says only "The initial filter state is 0", and Web Audio automates coefficients continuously without a reset, so resetting may kill a click but diverge from the Chromium behaviour §2.3(c) defines as parity. Decide which the golden vectors encode first.
- **Rejecting `rdev`** — last released 2023-06-26, verified exactly, and §7.6(4) forbids git dependencies so fixes living only on HEAD are unreachable.
- **`x11rb` over `xcb`** — on security grounds alone. x11rb carries `#![cfg_attr(not(feature = "allow-unsafe-code"), forbid(unsafe_code))]` and has zero RustSec advisories ever; `xcb` has three advisories including four CVEs, all stemming from being a C wrapper. Enable only `["xfixes", "shape"]`, never `all-extensions`.
- **`image` over the alternatives, and setting its limits.** PNG is a spec with adversarial history, `png` has 202M downloads, and image-rs is a live OSS-Fuzz project. Swapping to `zune-image` (85,963 downloads) to save build time would be the wrong trade under this project's own weighting. `fast_image_resize` is unnecessary — avatars go to the GPU sampler. And the hat-fetch exposure is smaller than §6.4 implies: `HAT_COLLECTION_URL` is pinned to a specific commit hash, so the bytes are content-addressed and immutable per release. A sandbox process is not warranted; the size limit, timeout and `image::Limits` are — plus a note that bumping `HAT_COLLECTION_COMMIT` is a security-relevant change needing review.
- **`socketioxide`'s extractor semantics genuinely fix the malformed-payload class.** Verified in source, not docs: `handler/message.rs` returns before invoking the handler on any extraction error, every handler is `tokio::spawn`ed so a panic is confined to one task, and `src/extract/` contains zero `unwrap()`, `panic!` or `expect(`. One imprecision to fix: §3.4 credits `#[serde(default)]`, but that makes deserialization *more* permissive. The protection is the early return. Use plain required fields with explicit bounds.
- **`egui` over the alternatives** — right conclusion, wrong reason (see §2.11).
- **Protocol compatibility.** `package.json` pins `socket.io-client ^4.8.3` → Socket.IO v5 / Engine.IO v4; socketioxide's default is v5 and it supports socket.io js from 3.0.0. 1.x Electron clients and 2.x Rust clients both work unchanged. **Do not enable the `v4` feature** — it adds engine.io v3 support the project deliberately dropped, and changes default-namespace deletion semantics.
- **`tokio`, `tracing`, `thiserror`, `anyhow`, `raw-window-handle`, `egui_extras`, `hound` as a dev-dependency, `cargo-audit`, `cargo-fuzz`, `cargo-nextest`, `axum`, `tower-http`'s absence aside** — all correct and current, with no open advisories at the pinned versions. Two notes: `anyhow` 1.0.104 is clear of RUSTSEC-2026-0190 (unsound `downcast_mut` after `context`, patched 1.0.103) by exactly one release, which is a good argument for caret + lockfile over an exact pin; and `raw-window-handle` 0.6.2 is 27 months old because it is finished — §7.6's "nothing unmaintained" stance needs a stated exception for crates like it and `realfft`, or a reviewer will keep re-raising them. `cargo-nextest`'s process-per-test isolation also fits §6.2's per-peer panic-isolation requirement, which is a better reason than speed.
- **`cargo-dist` 0.32.0 is correct in name and version.** The tool was renamed `cargo-dist` → `dist` in October 2024 but the crates.io package is still `cargo-dist`; the crate literally named `dist` is an unrelated abandoned 2016 statistics crate at 0.0.0. The real risk the plan does not state is that development is now effectively one human (Misty De Meo) plus dependabot, with axo.dev's blog and docs subdomains dead. That is manageable because the output is checked-in GitHub Actions YAML — **write that exit down**, and it converts a bus-factor-1 dependency into an acceptable one.

## 5. What the plan does not mention at all

**Security**

- **The AEC reference-signal path.** AEC3 needs the render (far-end) signal aligned with the capture signal, and the render side here is a mixed multi-peer output produced *after* the DSP graph. Neither §3.2's threading diagram nor §3.3's pipeline shows how the far-end reference reaches the APM. Getting that alignment wrong is the most common cause of an echo canceller that silently does nothing — and it will not fail a test, it will just not work.
- **A hostile or compromised signalling server can redirect all media.** §4 correctly schedules porting `validateClientPeerConfig` with its tests, but §6.3 never draws the conclusion. That function checks *shape* — urls present, credential is a string, url parses — not *trust*. Combined with §6.3's own "the server is unauthenticated", whoever controls the signalling server can set `forceRelayOnly` plus a `turn:` URL they own and route every lobby's audio through a relay of their choosing. DTLS-SRTP still protects confidentiality end to end, so this is metadata and availability, not eavesdropping — but it is the only place the port inherits a trust decision it cannot check, and it belongs in §6.3 in one sentence.
- **Fuzz the game reader, not just the RTP path.** §6.2 scopes cargo-fuzz to RTP → jitter buffer → decode. `ProcessMemory` is already a trait, so a fourth implementation alongside `ReplayProcess` — a `FuzzProcess` backed by `Arbitrary` bytes answering from a sparse map — makes `AmongUsState::read_from` fuzzable for almost nothing. Two hazards reachable today from a modded or corrupted game process: a self-referential pointer chain (infinite loop) and an attacker-influenced array length used to size a `Vec` (OOM). Cap chain depth and element counts. For this to find anything the parsing layer must be pure: `&dyn ProcessMemory` in, `Result` out, no `unwrap`, no `as` truncation.
- **`OpenProcess(PROCESS_ALL_ACCESS)`** — ~~`native/memoryjs/lib/windows/process.cc:24` opens the game with full access.~~ **Fixed 2026-08-24, in the shipping client rather than the port.** It now asks for `PROCESS_VM_READ | PROCESS_QUERY_LIMITED_INFORMATION`; `PROCESS_VM_WRITE | PROCESS_VM_OPERATION` and `PROCESS_CREATE_THREAD` are not requested at all, because the injection path that wanted them was removed. Called the cheapest security improvement in the whole port when this was written, and it cost one constant.
- **The MSVC 32-bit alignment footgun lands squarely on `acl-game`.** `i686-pc-windows-msvc` is Tier 1 with host tools, but carries the footnote that native C code on this target can align >4-byte types to only 4 bytes, and "this can still cause unsoundness due to unsafe code that (correctly) assumes that references are always properly aligned". Consequence: never use zerocopy's reference APIs (`ref_from_bytes`, `try_ref_from_bytes`) on any struct containing `u64`/`i64`/`f64`. Use `read_from_bytes`, which copies. Make it a clippy `disallowed-method` lint. The copy costs nothing — tens of bytes at 30 Hz.
- **`[bans.build]` is missing from the cargo-deny policy.** §6.1's supply-chain table promises "install-time script execution: 6 packages → build.rs only, auditable", and §7.6(3) lists advisories, licences, duplicate majors and sources — with no clause about build scripts or proc macros, which are the actual code-execution vector in a Cargo build. cargo-deny 0.20.2 already ships the enforcement: `allow-build-scripts`, `executables = "deny"` (reads file headers, so it works on Windows), `interpreted = "deny"`, `include-dependencies = true`, and per-crate SHA-256 `bypass` entries. Budget the bypass list as day-one work — `opus` and `webrtc-audio-processing` will fail immediately. And be honest about the ceiling: cargo-deny's own docs say it cannot catch a build script that fetches from a remote server in vanilla Rust. It raises awareness; it is not a sandbox. Relatedly, `libwebrtc`'s build-time download of a prebuilt binary zip is **not** covered by §7.6 as written — the "no source other than crates.io" rule is about Cargo.toml sources, not build-script network access. That is a gap in the policy to close, not a violation to cite.
- **Licence clarifications that will fail the first CI run:** `aws-lc-sys` declares `ISC AND (Apache-2.0 OR ISC)`; `ring` declares `Apache-2.0 AND ISC` over an OpenSSL-derived LICENSE file that is not cleanly SPDX-expressible; `webrtc-audio-processing` uses `license-file = "COPYING"` and reports as non-standard; `directories` pulls `option-ext` under **MPL-2.0** through `dirs-sys`, which the plan never mentions anywhere. All four need explicit `deny.toml` entries. (`dirs-sys` 0.5.0 also declares `windows-sys = ">=0.59.0"` — unbounded above, so the 0.100 restructure enters the tree on a `cargo update`. And `dirs-dev/directories-rs` is archived on GitHub, moved to Codeberg, with no code commits since the 6.0.0 release — record that so nobody sees the archived banner mid-release and panics.)
- **Exploit mitigations Rust leaves off by default.** Rust on MSVC gets ASLR and DEP, but `-C control-flow-guard` is off by default on stable and CET needs `/CETCOMPAT` at link time. Chromium ships with CFG on. Add to `.cargo/config.toml` for the Windows targets: `rustflags = ["-C", "control-flow-guard=yes"]` and, for x86_64, `"-C", "link-arg=/CETCOMPAT"`. Free, and the one place the port can be measurably *more* hardened than the document assumes.
- **PartitionAlloc.** Chromium runs its C/C++ on a hardened allocator — guard pages, freelist pointer encoding, per-bucket type isolation, address-space reservation on decommit. A Rust binary runs libopus and the bundled APM on the plain system allocator, and Rust's memory safety does not cross FFI. The precise code that *keeps* its memory-unsafety is the code that *loses* its allocator hardening. Either link a hardening allocator globally (mimalloc in secure mode) so the C/C++ inherits it, or state the acceptance explicitly.
- **RustSec does not systematically track CVEs in C vendored inside `-sys` crates**, and the plan's entire dependency-security story assumes it does. Verified asymmetry: `openssl-src`, `aws-lc-sys`, `audiopus_sys` and `ring` have advisory pages; `opus`, `libz-sys` and `curl-sys` have none. So `cargo audit` will **not** tell you when libopus or the bundled WebRTC APM tree has a security release. Today, one `electron` bump patches libopus, libvpx, BoringSSL, libpng and the whole WebRTC stack at once with CVE numbers and a public feed. After the port that becomes a named human responsibility with a named upstream watch list, and there is no such item anywhere in the plan.
- **§6's "net security win" claim does not survive scrutiny as written, and should be rewritten before anyone leans on it.** Three parts.
  (a) *The sandbox objection is weaker than it looks, and this cuts in the plan's favour.* Electron documents that `nodeIntegration: true` disables renderer sandboxing, and the current app sets exactly that. The renderer running WebRTC, Web Audio, Opus decode and hat-image decode is **already unsandboxed**. Moving those parsers into an unsandboxed Rust process is not a sandbox regression, because there is no sandbox to lose. §6.1 should say this explicitly — as written it invites the obvious rebuttal and has no answer prepared.
  (b) *The C/C++ arithmetic runs the wrong way.* The port is credited with removing 4,390 lines of hand-written C/C++ — true — but §6.2 concedes it **adds** libopus and the bundled APM C++ tree (AEC3 alone is an order of magnitude larger than 4,390 lines), and with rustls defaults it adds `aws-lc-sys`, a BoringSSL-derived tree RustSec filed five advisories against on a single day in March 2026, three of them HIGH (RUSTSEC-2026-0044 through -0048). Net C/C++ in one address space goes **up**, and unlike today none of it is in a separate process. The port's real supply-chain win is npm→crates.io immutability and install-time-scripts→auditable build.rs. That is a good and defensible win. "4,390 lines of C++ become code the compiler checks" is not, and it will not survive a competent reviewer.
  (c) *The largest genuine loss is Google's continuous fuzzing of exactly these parsers*, and §6.2 buries it in a subordinate clause. libopus, WebRTC's RTP/RTCP depacketizers, NetEQ, BoringSSL and the image codecs are on ClusterFuzz/OSS-Fuzz continuously at a scale measured in CPU-years. `neteq` (38k downloads) and `webrtc` 0.20.3 are not, and cargo-fuzz in CI is not the same order of magnitude. Make it the headline risk of §6.2. Conceding it plainly improves the document's credibility.
  (d) *And the concrete place the Rust client is weaker, stated plainly:* combining §6.3's admission that the client may run elevated with (b) and PartitionAlloc, the Rust client is **one process, elevated, unsandboxed, containing the RTP/SRTP parser, the Opus decoder, the jitter buffer, the image decoder for remotely-fetched hats, the TLS stack, and a process-memory writer**. Today those are at least spread across Electron's main/renderer/utility processes even though none is sandboxed. Fixes, cheapest first: never elevate by default (only the feature-gated injection path needs it — make elevation a per-feature runtime prompt); never decode remotely-fetched hat images in the elevated process; and as a roadmap item, put the RTP receive path in its own low-privilege process. RTP is the only byte stream an arbitrary internet peer can push directly into you, and that process boundary is the one thing Chromium gives you that a single Rust binary cannot fake.

**Performance**

- **Congestion control and bandwidth estimation are never mentioned.** §2.1 correctly lists everything else Chromium supplies free and omits this. `rtc-interceptor` ships NACK, SR/RR and TWCC record/report but **no bandwidth estimator and no pacer**; str0m has a full GCC-style estimator plus a pacer. Exposure is bounded — Opus at 24–64 kbps is near-CBR — but in a ten-player mesh a client uploads nine simultaneous streams with nothing to back off with on a constrained uplink. State explicitly that the plan accepts fixed-bitrate Opus with no rate adaptation, and add a ten-player-mesh-on-throttled-uplink case to §5's network emulation harness. If adaptation is later needed, the answer is not to write a congestion controller — it is to drive `opus_encoder_ctl(OPUS_SET_BITRATE)` from the TWCC feedback and per-peer RTCP loss webrtc-rs already reports.
- **Comfort noise on the receive side.** §2.3(b) says to enable Opus DTX to match the browser. DTX without CNG on receive sounds like the line dropped. `neteq`'s public module list has `expand`, `time_stretch`, `delay_manager` and `buffer_level_filter` — no `comfort_noise`, no `merge`, no background-noise estimation.
- **Denormal handling on the audio thread.** A reverb tail decaying toward zero produces denormals, which cause order-of-magnitude CPU stalls on x86 and are a classic source of dropouts. Neither flush-to-zero nor a crate that handles it is mentioned.
- **Real-time-safe API selection is nowhere in the coding rules.** §3.2 rule 1 says the callback never allocates, and the debug allocator in CI is the right enforcement — but the plan never says *which* APIs satisfy it: `opus::decode_float(&mut [f32])` and `encode(&[i16], &mut [u8])` write into caller-owned slices while `encode_vec`/`decode_vec` allocate; `rubato`'s `process_into_buffer` is safe while `process` allocates; `realfft`'s `process_with_scratch` with preallocated scratch is safe while `process` allocates. Write these into the rules next to the allocator check. Also: **never log from the audio callback** — a `tracing::warn!` formats, allocates and takes the subscriber's lock. Route callback diagnostics out over the SPSC queue and log on the consumer side.
- **A VAD decision.** The plan hand-writes an `AnalyserNode` purely to feed a VAD, when both candidate APMs already produce a voice-activity decision from a better algorithm (sonora's AGC2 uses an RNN VAD). That is duplicated work with a worse result, and possibly a whole node that need not exist.
- **The ConvolverNode is the one DSP node that should be a crate.** The plan justifies hand-writing five nodes because each is "five documented formulas". Four of them are. The convolver is not a formula, it is an algorithm with a performance requirement: uniformly partitioned FFT convolution with correct overlap-add accumulation, correct latency alignment, and no allocation or denormal stalls in the callback. Its failure modes are quiet — a reverb tail slightly late, slightly smeared or slightly quiet produces no crash, no test failure, and no bug report anyone can articulate. `fft-convolver` 0.4.0 (MIT, a pure-Rust port of HiFi-LoFi/FFTConvolver, states explicitly that it is real-time safe) does the hard general part; apply the Web Audio normalisation scalar yourself, which genuinely *is* one line the spec gives. *(Confidence: this recommendation was **not** independently re-verified by the second pass — treat the crate's real-time-safety claim as its own, and check denormal flush-to-zero, which `rt-fft-convolver` advertises and `fft-convolver` may not have.)*
- **No idle-repaint policy, despite idle resource use being a headline claim.** eframe is reactive and parks on `ControlFlow::Wait`, so a still window is near-0% CPU — but a UI driven from game state will call `request_repaint` somewhere, and calling it unconditionally in `update()` gives continuous mode at display refresh forever. The correct configuration is `ctx.request_repaint_after(Duration::from_millis(200))` driven off the game-state watch channel, with a much longer interval when minimised or occluded (egui #3982 was ~17% CPU when minimised on Windows; #7401 on pure_glow is still open). Note the honest scope: §2.4 claims installed footprint and idle *memory*, not idle CPU, and already flags itself "Estimated, not measured". Promote that caveat into §5 as a real gate with numbers for idle CPU, RSS, GPU memory and cold start on all three targets — taken from the current Electron build first.
- **No GPU fallback.** Chromium currently gives every user SwiftShader for free. A wgpu-only client gives users on RDP sessions, VMs and old integrated GPUs a failure to launch; `force_fallback_adapter` maps to DX12 WARP on Windows and has a reported rendering defect (gfx-rs/wgpu#2503), and eframe has no documented automatic wgpu→glow fallback. Ship both renderers compiled in behind a `--renderer glow|wgpu` flag. Also: set `default-features = false` on eframe and name the features — wgpu became the default only in eframe 0.34.0 (2026-03-26), and inheriting a renderer is not a decision.
- **`accesskit` is on by default in eframe 0.36.1** and the plan never mentions accessibility either way. Decide deliberately; Electron gave it for free.
- **`--locked` in every CI cargo invocation.** The plan commits `Cargo.lock` but never says CI must fail rather than update it. A lockfile CI silently regenerates is not a lockfile.
- **The ~250–350 crate estimate in §2.4 and §6.1 is too low.** The networking domain **alone** resolves to 272 crates as the plan is written (228 with the fixes above). Adding cpal, opus, the APM, neteq, rubato, realfft, symphonia, plus eframe/egui/winit/wgpu, plus windows/x11rb/sysinfo puts the real figure well past 350. This does not change the port's merits, but §6.1's supply-chain table compares 699 npm packages against "~250–350 crates" and that comparison will not survive first contact with a real Cargo.lock. Measure it at the end of phase 1 and requote.
- **`cargo-fuzz` needs nightly and is Linux-only** in the usual configuration, which conflicts with §7.1's single pinned stable channel and the three-target CI matrix. One sentence in §7.1 now, rather than a surprise in phase 4.
- **Wayland.** The plan's one sentence is a third true. winit's Wayland `set_cursor_hittest` does work (it sets an empty `wl_surface` input region, core protocol, no extension). But under native Wayland a client cannot position a window at absolute screen coordinates, cannot discover another client's window geometry, and cannot read global key state — none of which is solvable by a crate choice. The practical answer: Among Us on Linux runs under Proton/Wine, so in a Wayland session it is an **XWayland client with a real X11 window**. Force the client onto winit's X11 backend on Linux, talk to the XWayland display, and both the overlay and the `XQueryKeymap` poll keep working. Declare native-Wayland-only sessions unsupported with a startup diagnostic.
- **Two additions worth one config line each:** `cargo-auditable` (embeds the dependency list in the shipped binary so `cargo audit bin` works on an artefact months later — cargo-dist already integrates it) and cargo-dist's `github-attestations = true` (Sigstore-backed, logged to Rekor, verified with `gh attestation verify`, free on a public repo with no certificate). That pair answers "prove this binary came from this commit" better than chasing bit-for-bit reproducible builds across three targets, which is not a realistic phase-1 goal. Also add `cargo-about` 0.9.2 — cargo-deny enforces licence policy but does not produce the third-party attribution file GPL distribution wants. *(Not missing, and the plan is right to omit it: `cargo-semver-checks`. It verifies a published library's public API. This is an application and the workspace crates are not published.)*

**Also missing from `03-target-architecture.md`:** §7.2 lists `x11rb` for "XFixes input regions" and §3.3 says the Linux overlay "keeps the explicit XFixes path ported from `native/electron-overlay-window/src/lib/x11.c`". The audit reports that file includes only `<xcb/xcb.h>`, links only `-lxcb`, and contains no XFixes or Shape code — click-through today comes from Electron's `setIgnoreMouseEvents`. *(Confidence: the file exists at 11,398 bytes, but its **contents were not independently re-verified** by the second pass — check it before rewriting §3.3.)* If it holds, this is new code rather than a port and the estimate should say so. Separately, §3.3's claim that winit's `set_cursor_hittest` is "window-manager dependent and known to be unreliable" on X11 is wrong: winit's X11 implementation calls `shape_rectangles(SO::SET, SK::INPUT, ...)`, so the input shape is set by the **X server**. What *is* window-manager dependent is the other half of an overlay — `_NET_WM_STATE_ABOVE`, override-redirect, staying above a fullscreen game. The plan conflates the two. Keep x11rb; use winit for click-through and x11rb for the EWMH tracking `x11.c` actually does.

**One closing note on process.** The single most valuable thing to do with this document before phase 1 is not any individual crate swap. It is to run two cheap experiments that de-risk the two most expensive phases: a `cargo build --target i686-pc-windows-msvc` of whichever APM wins, and a transparent click-through window on all three targets. Both are hours. Both are brutal to discover in month nine.
